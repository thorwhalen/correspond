correspond.channels.telegram#

Telegram: a bot over the Bot API, with the standard library.

References

telegram: (the bot’s whole update stream, for listening), telegram:<chat id> (a private chat, a group or a channel; telegram:@name for a public channel), telegram:<chat id>/<topic id> (a forum topic).

Bots have no history API, and Telegram keeps undelivered updates for at most 24 hours, so poll writes every update it receives to a local log under the data root (telegram/) and read reads that log (a telegram:@name reference is first resolved with getChat, over the network). getUpdates confirms updates for every chat at once, which is why listening is account-wide: narrow to one chat when routing.

Senders are platform: Telegram authenticated the account, and correspond pulled the update from the Bot API itself. The bot token never appears in an error or a plan.

Webhook delivery, for a server: Telegram.set_webhook() asks Telegram to POST every update, one at a time, to an HTTPS address, carrying the configured webhook_secret in the X-Telegram-Bot-Api-Secret-Token header. mk_webhook_app() is the receiver, an ASGI app that stores each update carrying that secret under the data root (telegram-webhook/), in the order it arrives; the secret is the gate, and nothing without it is stored. serve_webhook() runs it (with uvicorn, the server extra) on 127.0.0.1 behind your own HTTPS reverse proxy, and refuses any other address unless webhook_allow_remote is set. With delivery = "webhook" in the config, listen reads what the receiver stored instead of calling getUpdates: Telegram serves one or the other, never both, so while a webhook is set getUpdates is refused (409), and Telegram.delete_webhook() returns the bot to polling. Telegram.verify() grades one delivery by the same header.

audience(ref, *, draft=None)[source]#

Who reads a chat, from getChat; a topic has its chat’s readers.

  • A private chat: named, the other account (by its id only, so a rename keeps the hash) as its reader.

  • A chat with a public username: public.

  • A group or supergroup without one: group; a channel without one: group of its subscribers. Members are never listed.

  • A linked chat (a channel’s discussion group, or the channel a group discusses) is read too: posts are copied into it. A public linked chat makes the audience public; one that cannot be read makes it unknown.

Joiners read the history unless getChat says the history is hidden from them. Forwarding widens every chat unless its content is protected. A failed getChat raises, so the audience resolves to public, defaulted.

correspond.channels.telegram.mk_webhook_app(*, secret, updates=None, max_body_bytes=1000000, clock=<built-in function time_ns>)[source]#

The webhook receiver as an ASGI app: Telegram POSTs updates, the app stores them in updates.

A request without secret in X-Telegram-Bot-Api-Secret-Token is refused (401) and nothing is stored: the secret is the only gate, since behind a reverse proxy every connection comes from this machine. Each update is stored under <arrival time in ns>-<update id>.json, so listen takes them in the order they came, whatever their ids (Telegram restarts them at random after a week without updates). One receiver process per bot keeps that order: Telegram.set_webhook() asks Telegram for one connection at a time. updates defaults to files under the data root (telegram-webhook/), which listen reads when delivery is webhook.

Return type:

Callable[..., Awaitable[None]]

correspond.channels.telegram.serve_webhook(*, host='127.0.0.1', port=8081, allow_remote=None, app=None, run=None)[source]#

Run the receiver (with uvicorn) on host, this machine unless allow_remote.

allow_remote defaults to the webhook_allow_remote setting. Put your HTTPS reverse proxy in front: Telegram reaches only public HTTPS addresses. Proxy headers are ignored, since the receiver needs no client address, and one worker keeps the order.
