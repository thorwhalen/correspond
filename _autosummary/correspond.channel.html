correspond.channel#

Serve listeners as a Claude Code channel: new messages pushed into a running session, replies through the ordinary tools.

Run correspond-channel (install the extra first: pip install "correspond[mcp]"). It is an MCP stdio server that declares experimental['claude/channel'], polls correspond.listen() for the conversations it was given, and emits one notifications/claude/channel per new message, from an allowlisted sender, as:

{"content": "<the text>",
 "meta": {"channel": "github", "conversation": "github:example/demo#1",
          "message_id": "...", "sender": "github:ada", "grade": "platform"}}

which Claude sees as <channel source="correspond" channel="github" ...>text</channel>. Meta keys are identifiers only (Claude Code silently drops a key with a hyphen).

Replies are the ordinary correspond tools (correspond.tools, through correspond.mcp.mk_server()): the reads by default, the writes only with --allow-send, each write dry-run first and through the operator’s before_send check.

Senders. Only messages from senders on the allowlist (--allow github:ada, matched on the sender’s attested address or <channel>:<native id>, never the room) are forwarded; an empty allowlist forwards nothing unless --allow-any-sender opens it. A forged message is never forwarded, the bot’s own messages never loop back, and events without an attested sender (a bare reaction) are not forwarded.

Permission relay (claude/channel/permission). With --relay-to <ref> (which needs --allow-send, because relaying is a send) the server declares the permission capability; each notifications/claude/channel/permission_request is sent to that conversation as a prompt ending in Reply "yes <id>" or "no <id>"; and a reply in that conversation of that shape becomes a notifications/claude/channel/permission verdict, never chat, but only when its sender is on the explicit allowlist (--allow-any-sender does not count), its authenticity grade is one of APPROVE_GRADES (authenticated: not claimed or forged), and the id is one this server relayed and has not yet answered.

How the Python MCP SDK does this (mcp 1.27, fastmcp 3.3, verified by the tests):

  • Declaring the capability: the low-level mcp.server.lowlevel.Server takes it as create_initialization_options(experimental_capabilities={"claude/channel": {}}); FastMCP (what py2mcp builds) keeps a public experimental_capabilities dict that its low-level server merges into the same call. This module sets that dict.

  • Emitting a custom method: ServerSession.send_notification only model_dump``s its argument into a ``JSONRPCNotification, so any model with method and params (mcp.types.Notification) goes out unvalidated. A background task has no session handle in FastMCP, so this module writes the same SessionMessage(JSONRPCNotification(...)) onto the transport’s write stream, after the client’s notifications/initialized.

  • Receiving a custom method: the SDK validates incoming notifications against the closed ClientNotification union and drops anything else with a warning, so permission_request is taken off the read stream by a tap in front of the session.

correspond.channel.notifications(refs, *, gate, cursors=None, registry=None, seen=None, pending=None, limit=None, seen_limit=10000, log=<function _log>)[source]#

One poll of every ref: the notifications its new events become, deduplicated on delivery id.

Lazy on purpose: correspond.listen() stores an event’s cursor only when the next one is asked for, so a consumer that emits each notification before asking for the next one gets at-least-once delivery, and seen makes it once per process. A ref that fails is logged and skipped; the others are still polled.

Return type:

Iterator[dict]
